## Recovery policy is an explicit owner choice

Legacy version-1 approvals retain their independent DR manifest, evidence bundle, independent custody receipt and actual restore gate. Version 2 may select `INDEPENDENT_DR_V1` with exactly those same guarantees, or select `SUPABASE_MANAGED_PHYSICAL_V1`. There is no fallback on failure or missing files. Managed policy v1 supports only verified database-backed files: nonzero external objects/references block it. A separate object-recovery manifest hash with self-declared counts is insufficient; activating such coverage requires its dedicated qualified recovery protocol.

Managed physical policy requires a private, SHA256-bound authoritative observation of a `COMPLETED` physical backup with an actual reference, exact Production identity, current observation (one hour), and documented seven-day Pro daily retention. The owner must select the maximum backup age, accepted recovery-point gap (at most 24 hours), minimum remaining retention and every residual risk. The actual observed gap must fit both selected limits. Approval must bind exact execution SHA/ref, migration bytes, policy/evidence digest, maintenance decision and expiration (at most 24 hours). Revalidation occurs before opening the database and again under the migration locks before source snapshots.

The result is **MANAGED_PHYSICAL_POLICY_PASS**, never RESTORE_PASS. It does not prove independent recovery, key custody or a performed provider restoration. Provider dependency, project-wide restore downtime/impact (including other schemas), recovery-point data loss, custom SQL role-password recovery and the exclusion of external object bytes remain explicit accepted risks. No restore-test project, PITR purchase or restoration is initiated.

Official references checked 20 October 2026: [backups, Pro retention, restore scope and Storage exclusion](https://supabase.com/docs/guides/platform/backups), [read-only backup-list API and backups_read permission](https://supabase.com/docs/reference/api/v1-list-all-backups). External Storage requires separate verified object recovery coverage even if its metadata is in PostgreSQL. Database-backed document bytea rows remain database data. Unknown/missing reference coverage blocks this release gate.
