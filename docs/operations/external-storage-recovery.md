# Phase 2B-0 — private external Storage byte recovery

Scope: project `xgetzgixalrsmuvfthpf`, database `postgres`, schema `visa_os`, the four existing objects in private bucket `documents`, 744452 declared bytes, created 5 August 2026 UTC. No deletion, upload, bucket change, SQL write, migration, account/role/key creation, Production deployment or restore project is part of this protocol. Nonmatching names are not proof of orphan status or deletion eligibility.

The authoritative read-only inventory now binds IDs, names, versions, update instants and declared byte sizes to an opaque object-set SHA256, and binds that digest to the full database/reference inventory. Shared evidence contains only aggregates and hashes; names remain in memory or inside the encrypted archive. Historical settings logos and all recognized archive-reference paths remain covered. More than four objects, another bucket, public objects, unknown references or missing/ambiguous database byte generations stop this bounded operation.

## Private operator

Use the existing Windows private credential mechanism. Required inputs are supplied only in an isolated operator environment, never arguments, Git, CI or chat:

- `EXTERNAL_STORAGE_AUTHORIZATION=OWNER_PHASE2B0`, `EXTERNAL_STORAGE_APPROVAL_REFERENCE=github-pr20-comment6292040915`, `EXTERNAL_STORAGE_PROJECT_REF=xgetzgixalrsmuvfthpf`.
- Existing authorized `DATABASE_URL`, `DATABASE_SCHEMA=visa_os`; verified TLS and exact database/project are mandatory. SQL runs only inside explicit read-only transactions.
- Preferred owner-selected input: `EXTERNAL_STORAGE_SIGNED_URLS_JSON`, a private JSON array of exactly four signed download URLs, one for each approved object. Supply it from masked local input / CurrentUser DPAPI or a qualified private provider response; never arguments, terminal output, chat, Git or CI. Each capability must use the exact Production Storage HTTPS host and bucket, have an issuance-to-expiry lifetime no greater than 900 seconds, and retain at least 90 seconds of validity. The whole set is validated before any object request; claims are scope/expiry checks, while the provider verifies the signature on the actual GET. No API key or Authorization header accompanies these requests. Wrong, duplicate, missing, expired or excessively broad links stop the operation.
- The existing `EXTERNAL_STORAGE_READ_TOKEN` mode remains available only with a separately authorized least-privilege object-read credential; supplying both modes is rejected. The owner's signed-link decision does not authorize retrieval of a broader Production server key. Never substitute an isolated Preview key or create a role/policy/token under this mandate. If no suitably authorized credential exists, actual object backup remains BLOCKED.
- `EXTERNAL_STORAGE_OPERATOR_SHA` is an exact CI-qualified clean checkout SHA.
- Private absolute `EXTERNAL_STORAGE_ARCHIVE_DIR` outside Git, normally the owner-private recovery vault on G:. Verify NTFS owner/SYSTEM-only ACLs, absence of reparse/cloud synchronization, accessibility and free space before access. Never place recovery files in a public artifact store.
- Existing `EXTERNAL_STORAGE_AGE_RECIPIENT` and its independently registered raw-file SHA256 in `EXTERNAL_STORAGE_AGE_RECIPIENT_SHA256`; owner identity path in `EXTERNAL_STORAGE_AGE_IDENTITY`, normally on distinct USB D:. `DR_LOCAL_AGE_BIN` selects the already qualified age executable. Never generate a new owner private key or copy the existing one.

Run `node --import tsx scripts/external-storage-backup.ts` from that clean checkout through the private wrapper. The child age process receives only an OS environment allowlist, never cloud credentials.

The operator captures the source set and references under READ ONLY, verifies exact count/bytes/private bucket/scope, downloads each object once with a serial pinned-host GET, bounded body and timeout, and refuses redirects/errors/size mismatch. It builds the complete private object manifest with actual payload SHA256 values and bytes only in memory. age encrypts it immediately; only complete ciphertext is persisted with exclusive creation. The operator reads the ciphertext back from disk, re-captures the current source in a **new** read-only transaction, and refuses any generation/inventory change. It then decrypts into memory with the owner's existing identity, checks every payload/hash/length, rejects omission/duplicates and emits an aggregate receipt. No unencrypted document or manifest file is created. A failed/interrupted operation is never reported successful; an existing ciphertext is never overwritten or automatically deleted.

The operator also writes an aggregate `.source-inventory.json` companion from its actual initial read-only transaction, with verified TLS. Use that exact companion when binding managed-backup evidence to the signed recovery receipt: its observation instant and inventory digest must match the receipt. A separately collected inventory with a different timestamp cannot substitute for it. This companion contains no object names, links or payloads.

The object archive and the provider database backup are not an atomic common point in time. That remaining gap must be explicitly accepted by the owner. A Storage provider restoration or database restoration is not performed by this local exercise.

## Signed release coverage is separate from merely possessing an archive

The normal result without a signing context is `UNSIGNED_LOCAL_RECOVERY_NOT_RELEASE_COVERAGE`. It can prove the private local exercise, but cannot open a release gate.

For an authenticated aggregate attestation, reuse the **existing** pinned RSA-3072 recovery recipient (`docs/consolidation/dr-backup-recipient.public-key.txt`, fingerprint `f82fa8d7fc09b01a2487a02a6d36d3937c3ade3d6ff0a84c205882bbdb526044`). No new owner key is generated. Only an already authorized private mechanism may deliver its private counterpart over private stdin with `EXTERNAL_STORAGE_ATTEST_EXISTING_OWNER_KEY=YES`. The operator checks the key identity and signs **only after actual decrypt/read-back**. If this private signing context is unavailable, the signed receipt remains BLOCKED; do not hand-author one or use a synthetic key.

`EXTERNAL_STORAGE_EXISTING_ARCHIVE` permits checking an existing private ciphertext, but never promotes its self-declared hashes. A fresh authorized provider download is still mandatory: recovered bytes must match that complete payload commitment and the fresh source generation. The private age identity's derived public recipient must equal the registered recipient before access. Replay then creates a **new** ciphertext encrypted only to that registered recipient, retains the original untouched, and verifies the new disk generation before attesting. File integrity, payload manifest, object-set/inventory, registered age recipient, clean operator SHA and timestamps are bound by an RSA-PSS SHA256 detached signature. The Production gate pins the committed verifier; no environment variable chooses another verification key. Synthetic signing keys are used only in offline tests.

`SUPABASE_MANAGED_PHYSICAL_V1` is unchanged in meaning: it cannot pass while external objects exist, and rejects self-declared recovered counts/manifest hashes. Independent DR semantics are unchanged.

The additional explicit option is `SUPABASE_MANAGED_PHYSICAL_SIGNED_OBJECTS_V2`. It requires all managed physical evidence, the separate raw signed-receipt SHA256, exact operator SHA and age-recipient digest, complete fresh source-set coverage and the existing owner's valid signature. It additionally requires exact acceptance of `OWNER_MANAGED_NOT_INDEPENDENT`, `NO_VERIFIED_OFFSITE_OBJECT_COPY`, and `OBJECT_AND_DATABASE_POINTS_NOT_ATOMIC`. A receipt cannot claim offsite verification or independent restoration. The current protocol proves **LOCAL_ONLY**, not geographical/offsite recovery. A future offsite proof must be qualified separately, never relabelled from a local copy.

The signed aggregate receipt is staged privately as `RELEASE_EXTERNAL_STORAGE_EVIDENCE` from `RELEASE_EXTERNAL_STORAGE_RECOVERY_JSON`; its raw SHA256 must equal `recoveryPolicy.externalRecoveryEvidenceSha256`. Freshness is rechecked under the existing migration locks. This preparation does not select the policy, populate approvals or arm either migration batch. Provider evidence, fresh source inventory, actual private byte recovery, explicit owner risk selection and later exact migration approvals remain mandatory.
